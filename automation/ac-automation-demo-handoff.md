# AC Project 自動化デモの引き継ぎ

対象リポジトリは `Aquarius0715/AC-Project`。専用ブランチで、仮データからエアコン運転の提案を作るデモを実装する。

## 1. 作業ブランチを用意する

既存の AC-Project を開いた WSL のターミナルで実行する。以下は `origin/main` から始める例。チームの合流先が別ブランチなら、確認したブランチ名に読み替える。

```bash
git status --short --branch
git remote -v
git fetch origin
git switch --no-track -c feat/automation-demo origin/main
git status --short --branch
```

最初の `git status` に変更が表示された場合は、ブランチを切る前に元のブランチでコミットするか、`git stash push -u -m "WIP before automation demo"` で退避する。Git は切り替え先と衝突しない未コミット変更を持ち越すことがある。退避した変更は元のブランチに戻ってから復元する。デモ用ブランチに切り替えたら、同じ VS Code ウィンドウで次の依頼文を Codex に渡す。

## 2. VS Code の Codex に渡す依頼文

### ゴールと作業範囲

AC Project のエアコン運転の提案ロジックを、リポジトリ直下の `automation/` に独立したデモとして実装してください。目的は、普段の使い方に合った快適な運転と電気代削減です。

- 最初に `git status --short --branch` とリポジトリの作業指示を確認してください。変更は `automation/` 内に収めてください。
- 仮データをローカルで読み込み、ケースを指定すると、提案の内容・理由・根拠、または提案を見送る理由を確認できる CLI にしてください。言語と実行方法は既存環境を見て、手軽に再現できるものを選んでください。
- 今回の実装範囲は提案の表示までです。既存Web・API・DB・実機への接続、承認の保存と運転予定への反映、付属リモコン対応、完全おまかせモードは後続です。コミット、push、PR、マージはユーザーが行います。

### ファイル構成

- `automation/README.md` に目的、動作要件、実行コマンド、データ形式、ケースごとの期待結果、仮ルール、実データへの接続方針を書く。
- `automation/data/` にケース別の仮データを置く。操作履歴、既存予定、気象、時間帯別料金、運転候補ごとの時間帯別消費電力量は、必要なケースに用意する。
- `automation/src/` にデータの読み込みと提案判定を置く。判定には整形済みのデータを渡し、取得元を後で差し替えられる形にする。

### 実装順と確認ケース

最初に「水曜の開始変更」と「証拠不足」の２ケースを通し、その後で気象と料金のケースを追加してください。初版のデモでは、履歴の集計と明示的な判定ルールを使います。

| ケース | 入力と期待結果 |
|---|---|
| 水曜だけ開始変更 | 現行は18:30開始、23:30終了。自動化設定前の直近４回の水曜のWeb手動オンが19:50、20:00、20:10、18:30なら、開始を20:00へ変更する提案を出す。４回中３回が20時前後だった理由を表示し、23:30終了を維持する。 |
| 証拠不足 | 20時前後の操作が１回だけなら、水曜の開始変更を見送る。曜日別の開始時刻では、まず仮に直近４回中３回が候補時刻の前後15分に入る条件を試す。 |
| 暑い日の温度 | 暑い日だけ24℃から22℃への手動変更が繰り返されるなら、暑い日に限った温度変更を提案する。１回だけ、または外気温との対応が不明なら見送る。気温と回数の閾値は仮の値としてREADMEに書く。 |
| 安い時間帯の予冷 | 普段の運転と予冷について、同じ比較期間で時間帯別の消費電力量 × 単価を合計する。仮データ上で必要な時刻に同等の快適さが見込め、合計額が下がるときに提案する。 |
| 単価は安いが総額が上がる | 予冷で運転時間や消費電力量が増え、同じ比較期間の合計額が上がる場合は、節約提案を見送る。 |
| 暑さと高い料金が重なる | 温度変更による快適性の提案と、電気代の見積もりをユーザーが区別できるように表示する。快適性を保てない予冷案は節約候補から外す。 |
| 旅行・一時変更・欠損 | 旅行期間と「今回だけ」の操作を普段の傾向から除外する。自動運転の実行をユーザーの好みに数えず、欠損で根拠が不足する場合は該当の提案を見送る。 |

Webの手動操作は、学習有効化より前の履歴も対象にする想定。対象機器、日時、操作元、オン・オフや温度変更を識別できるようにする。気象は対象日時の外気温を仮データで渡し、後で地点・時刻に応じた実測値や予報を取得する処理を追加できるようにする。金額と快適性は仮の消費電力量・室温などから比較した結果と分かる形で出す。

### 将来のつなぎ込みで引き継ぐ仕様

- 現在の予定を実行する仕組みは既存のオートメーション。学習結果は予定の追加・変更の提案として出し、理由と変更箇所を表示する。承認・修正して承認した内容だけを適用し、対象の予定を更新する。
- 承認と修正はユーザーの希望として記録する。見送りは同じ根拠での再提案を抑えるために使い、無反応から好みを推定しない。
- 予定の開始時刻にオフなら予定温度でオン、すでにオンならそのまま。開始後の手動オフではつけ直さない。「今日の開始をスキップ」した日も、後から手動でオンにしたら、通常は予定どおりの終了時刻にオフにする。
- 旅行などの停止期間に入るとオフにし、期間終了後は次の予定時刻から再開する。
- 将来の完全おまかせモードでは、既存の予定を一時停止して、学習結果に応じて承認なしで運転する。手動操作を優先する期間や再開条件は別途決める。

実装後は全ケースを実行し、結果が表の期待どおりか確認してください。最後に、実行コマンド、ケースごとの結果、READMEの場所、実データ接続時に必要な入力を報告してください。

## 3. デモを確認して push する

デモ用ブランチ上で実行する。未追跡ファイルを含めて `git status` で確認し、ステージした差分を見てからコミットする。

```bash
git status --short
git add -- automation/
git diff --cached --stat
git diff --cached
git commit -m "Add standalone AC automation demo"
git push -u origin feat/automation-demo
```

GitHub でチームの合流先をベースにしたPRを作る。デモの差分をレビューしてマージしたあと、別の作業で実データの読み込みと、承認済みの提案を既存オートメーションへ反映する処理をつなぐ。
