# エアコン運転の月次一括評価デモ

普段のWeb手動操作から、快適な運転と電気代削減に向けた予定変更を提案する、独立したローカルCLIです。履歴を集計し、明示的な仮ルールで「提案内容・理由・根拠」または「見送る理由」を表示します。すべて仮データであり、金額・室温・快適性は仮の見積もりです。実際の節約額や室温を保証するものではありません。

実装範囲は表示までです。Web・API・DB・実機との通信、承認の保存、予定の更新、付属リモコン対応、完全おまかせ運転は含みません。元の依頼は [ac-automation-demo-handoff.md](ac-automation-demo-handoff.md) にあります。

## 24顧客・30日分の月次評価

月次データは **2026-10-01〜10-30の連続30日、24顧客、1顧客1機器、30分ごと48区間/日**です。判定日時は`2026-10-31T12:00:00+09:00`に固定しています。2地点の天気と2料金プランを共有参照します。利用開始前の日も30日分の枠に含め、`not_enrolled`で表します。

既存の個別ケースCLIとテストも引き続き利用できます。Python 3.12以上の標準ライブラリだけで動きます。以下はすべてリポジトリ直下から実行してください。

```bash
# 全顧客の提案件数と状態。見送りは件数に含まない
python3 -B -m automation.src.cli --customers

# 0件、1件、同種の複数件、異種の複数件、準備中の詳細
python3 -B -m automation.src.cli --customer C001
python3 -B -m automation.src.cli --customer C002
python3 -B -m automation.src.cli --customer C003
python3 -B -m automation.src.cli --customer C021
python3 -B -m automation.src.cli --customer C014

# 操作・外気温・30分ごとのkWh×単価と日合計を照合
python3 -B -m automation.src.cli --customer C023 --day 2026-10-14

# 一覧は軽量なサマリーJSON、個別は全判定と区間料金を含むJSON
python3 -B -m automation.src.cli --customers --json
python3 -B -m automation.src.cli --customer C021 --json

# 別のデータファイルで再評価 / 判定日時をさかのぼって評価
python3 -B -m automation.src.cli --customer C002 --monthly-data automation/data/monthly/dataset.json
python3 -B -m automation.src.cli --customer C002 --as-of '2026-10-25T12:00:00+09:00'

# 再生成。同じseedならファイル内容まで一致する
python3 -B -m automation.src.generate_monthly --seed 42
# 既存データを保ち、別のseedを試す場合
python3 -B -m automation.src.generate_monthly --seed 43 --output /tmp/ac-monthly-43.json

# 従来の個別ケース＋月次の全期待結果・入力変更テスト
python3 -B -m unittest discover -s automation/tests -v
```

生成方法は [src/generate_monthly.py](src/generate_monthly.py) の`build_data`、入力は [data/monthly/dataset.json](data/monthly/dataset.json) です。`PROFILES`は手動開始時刻・在宅曜日・旅行・操作元などの**利用行動を生成する設定**であり、期待する提案や件数を判定器に渡しません。顧客IDと説明は識別・表示にだけ使います。期待結果は [tests/test_monthly.py](tests/test_monthly.py) の`EXPECTED`に置いています。

### 月次データの区別と整合性

[src/monthly_data.py](src/monthly_data.py) の`normalize_bundle`が共有参照、日付の連続性、機器と操作日、重複ID、区間数、測定値、予測候補と過去の判断を検証します。

| 入力 | 意味と扱い |
|---|---|
| `sites` | 地点IDごとにタイムゾーン、`observations`、`forecast`を共有。各行は日付・天気・48区間の外気温・発行/取得日時を持つ。観測相当値と予報相当値を混ぜない。 |
| `tariffs` | プランIDごとの48区間の`jpy_per_kwh`。この版は毎日同じ時間帯単価。各顧客はプランIDで参照する。 |
| `customers[].schedules` | 曜日0〜6の開始・終了・温度。空なら予定未設定。1曜日1予定、同日内の運転を扱う。 |
| `days[].operations` | ID・機器・オフセット付き日時・操作元・操作種別・今回だけ・変更前後の温度。温度が分かるオン操作は`to_c`を持つ。 |
| `operation_status` | `complete`=その日の操作記録がそろう、`missing`=取得欠損、`not_enrolled`=利用開始前。空の操作配列だけで未利用と決めない。 |
| `usage` | `used`=利用あり、`unused`=未利用を確認、`unknown`=不明。`unused`は操作なし・全区間既知の0kWhで検証する。 |
| `days[].kwh` | 過去の**観測相当**の消費電力量。配列の添字0が現地00:00〜00:30、47が23:30〜24:00。`0`と`null`を区別する。 |
| `predictions` | 将来の日付・生成日時・比較期間・必要時刻・快適性目標と、通常/快適性/予冷候補のkWh・必要時刻の室温・運転条件。過去の観測kWhとは別の入力。 |
| `judgments` | 提案日時・内容・根拠IDと署名・反応・反応日時・修正承認時の`selected`。顧客内の同じ種類・曜日・温度条件へだけ適用する。 |

観測電力は`measured_energy`で、オン/オフ/設定温度変更の間を分割して積算します。動作中の仮の消費電力は`(0.35 + max(外気温 - 設定温度, 0) × 0.06) × 機器係数 kW`です。30分途中の手動オンも稼働した時間だけ積算し、停止時は既知の0にします。機器係数は固定seedから生成し、暑さと低い設定温度で消費量が増える構成です。これはデータ生成用の簡易式で、実機の物理モデルではありません。

将来候補の予測は`prediction`で別に作る仮のシナリオ値です。今回の通常案は17:00〜23:00の同じ12区間で3.6kWh、安い予冷は3.1kWh、割高な予冷は9kWhです。必要時刻20:00の室温と目標±0.5℃を比較し、同等の快適性を満たす比較元から総額が下がる場合だけ提案します。C021では24℃の普段案120円は目標22℃を満たさないため、22℃の快適性案150円と予冷80円を比較し、70円減とします。快適性案の普段比30円増は別表示です。

候補予測には、前提にした地点の予報行の`weather_signature`を保持します。天気を変えたのに候補のkWh・室温を作り直していない場合は、古い予測を使わず「予測の再作成が必要」と表示します。モデル候補の停止区間に正のkWhがある入力も拒否します。

[src/monthly_engine.py](src/monthly_engine.py) の`billing`は、観測kWhから毎回`kWh × 単価`を計算します。区間に欠損があれば日合計・月合計を`null`とし、既知区間の小計を別に残します。`null`を0や無料として補いません。料金は入力単価による従量分で、税・基本料金・需要料金を別途足しません。

開始時刻・温度の変更について候補別予測が提供されていない場合、変更単独の電気代は「未見積」と表示します。観測料金を将来の節約額に転用しません。各提案は現行予定に対する独立した評価で、開始変更と予冷を合成した効果や、複数提案の節約額の合計は計算していません。

### 固定ルール・履歴から計算する値・過去の判断の違い

**機械学習のモデル訓練・パラメーター更新は行っていません。** 固定ルールに、毎回その時点の履歴と明示的な希望を渡して評価します。データの追加で集計結果と提案が変わりますが、閾値や予測式そのものを学習する方式ではありません。

| 分類 | このデモの処理と具体例 | コード |
|---|---|---|
| 固定の開始ルール | 直近4回の完了した対象曜日のうち、候補時刻の±15分に3日以上。1日につき最初の有効なWeb手動オンを1票とする。 | [engine.py](src/engine.py) の定数と`start_pattern`。既存個別ケースの`start_decision`も同じ集計を利用。 |
| 履歴から計算する開始 | 全7曜日を個別に走査。支持数最多・時刻差最小・同率なら早い候補。C003は月曜17:30と水曜20:00の両方を返す。 | [monthly_engine.py](src/monthly_engine.py) の`schedule_results` |
| 初回予定 | 現行予定がなければ、開始・その日の最後の手動オフ・オン時の温度について共通する3日以上を必要とする。終わりや温度を一律の既定値で決めない。C005では2曜日の予定を追加する。 | `schedule_results` |
| 固定の暑さルール | 操作±30分以内の最寄り観測外気温、32℃以上、異なる3日以上、同じ低い温度。涼しい日にも同じ変更があれば暑い日限定とはしない。 | [engine.py](src/engine.py) の`temperature_decision`, `matching_weather` |
| 履歴から計算する温度 | 現行温度ごとの曜日群を評価し、日ごとの最後の変更を使う。C006は履歴から22℃、操作を23℃へ変えれば23℃へ追従する。 | `temperature_results` |
| 固定の予冷ルール | 同じ期間のkWh×単価を積算、必要時刻の目標室温±0.5℃、厳密な総額減が条件。観測電力を候補予測に代入しない。 | [engine.py](src/engine.py) の`energy_decision`と`plan_cost`、`precool_results` |
| 明示的な希望 | 承認は提案値、修正承認は`values`に`selected`を重ねた値を優先。C015は操作の傾向20:00より、選んだ19:30を優先する。現行と一致すれば変更不要。無反応は支持にも拒否にも数えない。 | `judgments_as_of`, `apply_judgments` |
| 再提案の抑制 | 種類・曜日・変更値と根拠データの署名を比較。同じ根拠の見送りを抑制。C016は0件、C017は追加された10/28の操作を含め再評価。新しい承認は古い見送りに優先する。 | `signature`, `result`, `apply_judgments` |

根拠署名は開始なら該当4日と有効なオン、温度なら手動変更と対応する気温、予冷なら候補予測・予報・料金を含めます。現在時刻や他顧客の操作は含めません。料金だけの変更で見送り済みの開始案が再表示されることもありません。明示的な選択は後の明示的な選択まで優先し、通常の操作回数で上書きしません。承認済み予冷でも、今回の候補予測がその運転条件に対応し、快適性と費用の条件を満たすことを改めて必要とします。

旅行・今回だけ・自動運転・付属リモコンは普段の手動操作から除外します。`enrolled_at`以降かつ`as_of`未満の操作を使い、この版の月次判定は完了した日を集計します。判定日時より後の提案・反応は使いません。過去の提案に将来の反応が記録されていても、その時点では無反応として扱い、将来の`selected`を表示・適用しません。予報と候補予測も、その発行・生成日時が判定日時までのものを使います。

0件の状態は「変更の必要を示す根拠なし」「履歴不足で一部判定できません」「同じ根拠の再提案を抑制」を区別します。利用開始から7日未満で提案に足る根拠がない場合は「提案を準備中」です。準備中であっても、明示的な選択などで提案を出せる場合は提案を表示します。個別の`decisions`には`proposed / unchanged / insufficient / suppressed / unavailable / rejected`を残し、`proposals`には`proposed`だけを数えます。「変更不要」は満足を推定した意味ではなく、今回のルールで変更の必要を示す根拠がないという意味です。

### データを変えて確認するテスト

[tests/test_monthly.py](tests/test_monthly.py) は24顧客の件数・曜日・時刻・温度・予冷案を照合し、次の変更も検証します。

- `test_operation_only_changes_move_weekday_start_and_temperature`: 現行予定は固定し、水曜20:00、火曜17:00、暑い日23℃という操作の変更に提案が追従する。
- `test_fixed_cli_command_follows_only_operation_data_changes`: 同じ`--customer`・同じ`--monthly-data`・同じ実行コマンドを維持し、操作だけを書き換えて0→金曜21:00の1件になる。
- `test_weather_only_changes_remove_hot_day_proposal`: 操作を変えず外気温だけを涼しくすると、暑い日の温度案だけが消える。
- `test_tariff_only_changes_remove_savings`: 予冷する時間の単価だけを上げると節約案が消え、総額が下がらない理由が残る。
- `test_judgment_only_changes_approval_rejection_and_no_response`: 利用履歴を固定し、修正承認・見送り・無反応の違いを検証する。
- `test_changes_to_one_customers_operations_and_judgments_do_not_affect_others`: 2顧客の操作・判断を変更しても、他の22顧客の詳細結果は一致する。
- 生成の再現性、観測電力と稼働時間・天気・温度の整合、未利用と欠損、区間料金と日合計、未来データの除外、初回予定の根拠不足、予報と予測の前提不一致、快適性を保つ比較元も検証する。

実データ接続や本番反映は後続です。現在の30分グリッドは日本の2地点の24時間/日を前提にしており、実機の不規則なサンプル間隔、夏時間、料金プランの適用期間、複数機器・複数予定、室温予測の校正と不確かさは接続時に扱います。承認・見送りの新規保存や予定適用は行いません。

## 従来の個別ケース：動作要件と実行方法

Python **3.12以上**と、OSのIANAタイムゾーン情報が必要です。WSL / LinuxのPython 3.12.3で確認しています。標準ライブラリのみを使い、追加パッケージ・環境変数・Docker・ネットワークは不要です。

リポジトリ直下から実行します。

```bash
# 一覧、個別ケース、全ケース
python3 -B -m automation.src.cli --list
python3 -B -m automation.src.cli --case wednesday-start
python3 -B -m automation.src.cli --case insufficient-start
python3 -B -m automation.src.cli --all

# 機械可読JSON。出力は標準出力のみで、ファイルを更新しない
python3 -B -m automation.src.cli --all --json

# 別のローカルデータを使う
python3 -B -m automation.src.cli --file automation/data/cheap-precool.json

# 全ケースの期待結果と、判定・入力の境界条件のテスト
python3 -B -m unittest discover -s automation/tests -v
```

`-B`はPythonのキャッシュファイル作成を抑制します。`automation/`をカレントディレクトリにする場合は、`python3 -B -m src.cli --all`でも実行できます。終了コードは、正常終了（提案見送りを含む）が`0`、入力・引数エラーが`2`です。`--all`は結果を表示し、テストコマンドが期待結果を照合します。

| ケース名 | 期待結果 |
|---|---|

| `insufficient-start` | 20:00の操作が1回のみ。3/4回の条件を満たさず見送り。 |

| `insufficient-temperature` | 暑い日の24→22℃が1日。見送り。 |
| `missing-weather` | 温度変更は3日あるが気象との対応不明。見送り。 |
| `missing-temperature` | 変更前の温度が欠損。温度変更の提案を見送り。 |
| `temperature-not-hot-only` | 涼しい27℃の日にも22℃への変更がある。暑い日限定とは判断せず見送り。 |
| `cheap-precool` | 同じ17:00〜23:30の総額100→78円。20:00の予測室温はいずれも24℃。22円安い予冷を提案。 |
| `expensive-precool` | 予冷で使用量が増え、総額100→130円。安い時間帯を使っても見送り。 |
| `hot-expensive` | 暑い日の22℃を快適性のため提案。普段の24℃運転100円と、22℃運転132円の差32円を別表示。78円の予冷は20:00の室温23.5℃で目標22℃を満たさず除外。 |
| `excluded-history` | 旅行・今回だけ・自動運転・付属リモコン・別機器を除外し、有効な手動オンが1回なので見送り。 |
| `missing-energy` | 予冷の1区間のkWhが不明。ゼロ補完せず見送り。 |
| `missing-comfort` | 必要時刻の室温が不明。快適性を比較できず見送り。 |
| `missing-tariff` | 1区間の料金が不明。無料扱いせず見送り。 |

予冷の金額は次の積算です。kWhはその区間全体の消費電力量なので、区間の時間をもう一度掛けません。

| 時間帯 | 単価（円/kWh） | 普段（kWh） | 安くなる予冷（kWh） | 高くなる予冷（kWh） |
|---|---:|---:|---:|---:|
| 17:00〜18:00 | 10 | 0 | 1.2 | 4 |
| 18:00〜20:00 | 20 | 1 | 0.5 | 1.5 |
| 20:00〜23:30 | 40 | 2 | 1.4 | 1.5 |
| 合計額（円） | | 100 | 78 | 130 |

## ファイルと処理の分離

- `data/`: 実行ケース別のJSON。`as_of`を固定し、実行日の違いで結果が変わらないようにする。
- `src/loader.py`: ローカルJSONを読み、型・時刻・範囲・区間の整合性を検証して整形する。
- `src/models.py`: 取得元に依存しない、変更不可の入力・結果モデル。
- `src/engine.py`: 整形済み`Scenario`を受け取る判定。ファイル読み書き・外部通信は行わない。
- `src/cli.py`: ケース選択と、日本語またはJSONの表示。
- `tests/test_demo.py`: 全ケースの期待結果、除外、重複日、閾値、快適性、金額、入力エラーを検証する。

後で取得元を変更するときは、アダプター側で`Scenario`へ整形し、`evaluate(scenario)`に渡します。判定ロジックがDBや気象APIを直接読む構造にはしません。JSON出力の`check`は`start`・`temperature`・`precool`、除外の参考情報は`history`です。`proposed`、`reason`、`evidence`、`changes`と、温度提案時の`target_temperature_c`を返します。

## データ形式

すべての日時はUTCオフセットを含むISO 8601形式です。曜日と時刻の集計はケースの`timezone`で行います。機器のタイムゾーンはチャットや実行ホストのタイムゾーンとは独立です。サンプルは`Asia/Tokyo`を指定しています。

| フィールド | 内容 |
|---|---|
| `name`, `description` | ケース名と説明。文字列。 |
| `device_id`, `timezone` | 対象機器IDとIANAタイムゾーン。 |
| `as_of` | 判定の基準日時。これ以降の操作履歴は利用しない。 |
| `history_start` | 履歴観測期間の開始。履歴の対象は`history_start <= at < as_of`。 |
| `learning_enabled_at` | 学習有効化日時。来歴として保持するが、これより前のWeb手動操作を除外しない。 |
| `checks` | 判定の配列。`start`, `temperature`, `precool`から指定する。 |
| `schedule` | `weekday`（月=0〜日=6）、`start`, `end`（HH:MM）、`temperature_c`（16〜30℃）。この版では同日内の予定1件。 |
| `operations` | 操作の配列。機器ID、日時、操作元、操作種別、今回だけの指定を必須とする。 |
| `trips` | `start`以上`end`未満を停止期間とする配列。省略時は空。 |
| `weather` | 機器ID、日時、`outdoor_c`を持つ気象データ。省略または気温`null`は測定なし。 |
| `energy` | 料金・消費電力量・快適性の比較入力。省略時は節約提案を見送る。 |

操作1件の例です。

```json
{
  "device_id": "ac-living",
  "at": "2026-10-07T19:00:00+09:00",
  "source": "web_manual",
  "action": "temperature",
  "once": false,
  "from_c": 24,
  "to_c": 22
}
```

`source`は`web_manual`・`automation`・`remote`、`action`は`on`・`off`・`temperature`です。オン・オフでは`from_c`と`to_c`を省略できます。温度操作でこれらが不明なら、その日の温度変更は根拠に数えません。`once`は明示的な真偽値が必要です。操作元不明をWeb手動とみなすことはありません。

`energy`の形式は次のとおりです。完全な例は [cheap-precool.json](data/cheap-precool.json) と [hot-expensive.json](data/hot-expensive.json) を参照してください。

- `start`, `end`: 全候補共通の比較期間。予冷開始から通常運転終了までを含める。
- `required_at`: 快適さが必要な日時。比較期間内に置く。
- `comfort_target_c`: 必要時刻の目標室温。エアコンの設定温度と予測室温は別の入力として扱う。
- `slots`: `start`, `end`, `jpy_per_kwh`の配列。比較期間全体を時刻順に隙間・重複なく覆う。料金の測定欠損は`null`。
- `plans`: 固有の`name`、`kind`（`usual`・`comfort`・`precool`）、`kwh`、`indoor_c_at_required`の配列。普段の運転`usual`は必ず1件。`comfort`は快適性のため温度を変えた候補で、節約候補には数えない。
- `kwh`: `slots`と同じ要素数・順序の、その区間全体の消費電力量。明示的な`0`は停止などの既知のゼロ、`null`は不明。負数・非有限値は入力エラー。
- `indoor_c_at_required`: 必要時刻の仮の予測室温。`null`は不明。候補間で同じ日時・条件で求めた室温を渡す。

欠損測定は推測で補いません。JSON構造の不正、UTCオフセットなしの日時、区間の隙間・重複、配列長の不一致などは、比較不能な入力としてエラーを表示します。

## 仮の判定ルール

以下は初版のデモ用ルールであり、学習済みモデルや実機に合わせて校正した値ではありません。

1. **普段の操作**: 対象機器・観測期間内のWeb手動操作だけを使う。旅行期間・`once=true`・自動運転・付属リモコンを除外する。除外件数を表示する。除外や欠損を補うために古い曜日へさかのぼらない。
2. **曜日別の開始時刻**: `as_of`の現地日付より前の、完了した直近4回の対象曜日を使う。1日につき最初の有効な手動オンを1票とする。同日の再オンを別の日の証拠にしない。候補時刻の**前後15分以内に3回以上**が必要。分単位で候補を比較し、支持数が最多、時刻差の合計が最小、同率なら早い時刻を選ぶ。現行時刻と同じ、または終了以降なら提案しない。変更は対象曜日の開始だけで、終了は維持する。日をまたぐ時間差は扱わない。
3. **暑い日の温度**: 観測期間内で、各日の最後の有効な手動温度操作を使う。同日の連打は1票とし、後で元に戻した日は変更の支持に数えない。操作時刻の**前後30分以内**で最も近い対象機器の外気温を対応付ける。同距離の矛盾した気温は不明とする。外気温**32℃以上**の**異なる3日以上**で、現行設定から同じ低い温度へ変えた場合に、暑い日限定で提案する。32℃未満でも同じ変更先がある場合は、暑い日限定とは判断しない。気象や変更前後の温度が不明な日は数えない。温度ケースの集計期間は`history_start`〜`as_of`で、開始時刻の「直近4回」とは別。
4. **予冷の総額**: 各案について`sum(区間kWh × 区間の円/kWh)`を`Decimal`で積算する。実数のまま比較し、表示のみ小数2桁に四捨五入する。基本料金、税、需要料金などは含まず、入力単価による従量分の比較とする。
5. **快適性と節約の区別**: 必要時刻の仮の予測室温が目標の**±0.5℃以内**である案だけを、同等の快適性とみなす。冷えすぎも除外する。通常運転または快適性案のうち、この条件と総額既知を満たす最安の案を比較元にする。予冷は比較元より**総額が厳密に安い**場合だけ提案し、最安の予冷案を選ぶ。1区間でも料金・kWhが不明、室温が不明、または比較元が不明なら節約を主張しない。温度変更と同時に判定する場合は、温度提案と比較目標の一致も確認する。

このデモの快適性評価は必要時刻の室温1点だけです。湿度、在室期間全体の室温、建物の熱特性や予報誤差を評価しておらず、実際の快適性を検証したものではありません。温度提案を「電気代が安くなる」とは表示せず、快適性案の費用増減と、予冷での節約可否を分けて表示します。

## 実データへの接続で必要な入力と引き継ぎ仕様

まずアダプターで、次の入力を同じ基準日時・単位・機器へそろえます。

- **機器と現行予定**: 対象機器ID、現地タイムゾーン、対象予定ID・版、曜日別の開始/終了・設定温度。複数予定や日跨ぎ予定の扱いは接続時に拡張する。
- **操作履歴と除外**: 学習有効化前を含む履歴、機器ID、日時、操作元、オン/オフ/温度、変更前後の値、「今回だけ」、旅行などの停止期間、観測開始と判定日時。実データではイベントIDで重複排除し、取得漏れや自動実行との区別を保持する。
- **気象**: 機器の設置地点または地点ID、日時別の実測/予報外気温、取得日時・品質・欠損状態。現状の`weather.device_id`は、地点の実測や予報を機器に対応付けた結果を受け取るための簡略形。
- **料金と運転モデル**: 全候補共通の比較期間、時間帯別の適用単価（円/kWh）、各候補の区間消費電力量（kWh）、必要時刻と快適性目標、同条件の室温予測。予冷以外の期間も含めた総消費量を渡す。実機の消費電力・室温履歴でモデルを校正し、予測の不確かさも扱う必要がある。

予定の実行には既存オートメーションを使います。学習結果は予定追加・変更の提案として理由と変更箇所を示し、承認または修正して承認した内容だけを対象予定へ反映します。現デモの結果は表示用で、適用用のコマンドではありません。

承認・修正はユーザーの希望として記録します。見送りは同じ根拠での再提案を抑えるために利用し、無反応から好みを推定しません。実データ接続では提案ID・対象予定ID・元の版・根拠の識別子を保持し、古い予定への誤適用や同じ根拠の再提案を防ぎます。

運転側に引き継ぐ動作は、以下のとおりです。これらは今回のCLIでは実行しません。

- 予定開始時にオフなら予定温度でオンにし、すでにオンならそのままにする。
- 開始後に手動でオフにした場合はつけ直さない。
- 「今日の開始をスキップ」しても、後から手動でオンにしたら、通常は予定どおりの終了時刻にオフにする。
- 旅行などの停止期間に入るとオフにし、期間終了後は次の予定時刻から再開する。
- 将来の完全おまかせモードでは既存予定を一時停止し、学習結果に応じて承認なしで運転する。手動優先の期間と再開条件は別途決める。
