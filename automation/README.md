# 編集できる仮データと、日付順の運転提案レポート

100世帯×90日の入力を顧客別の非圧縮JSONで開き、各判定日の予定・操作・在宅情報・提案の根拠を、ローカルHTMLで確認する承認型デモです。完全オート、スマホの実位置取得、実機制御、承認の新規保存、本番予定への反映は行いません。

```text
automation/
  data/
    README.md                    入力の読み方・編集方法
    dataset.json                 seed、期間、判定時刻、参照ファイルの一覧
    customers/H001.json …        1世帯1ファイル。設置地点・住人・機器・予定の版・90日の記録・判断履歴
    weather/tokyo-east.json      共有する実測相当の天気と、発行日時付きの予報
    weather/kanagawa-west.json
    tariffs/time-of-use.json    共有する30分区間の料金単価
    tariffs/flat.json
  src/
    generate.py                 新形式への一括生成・整形済みJSON保存
    simulation.py, synthetic.py 仮の天気・操作・電力・スマホ観測の生成部品（ファイルは保存しない）
    dataset.py                  顧客別JSONの読込・検証・判定時点のスナップショット
    monthly_data.py, models.py  判定用の整形済みデータ型と検証
    presence_data.py            世帯・設置地点・スマホ観測・前後電源の検証
    presence.py                 住人と世帯の home / away / unknown 判定
    engine.py, monthly_engine.py 開始・温度・予冷・料金の既存ルール
    presence_proposals.py       不在の繰り返し、電源の実遷移、根拠の統合
    replay.py                   日次評価、過去の反応、提案の初回/継続/変更/終了の記録
    html_report.py, cli.py      オフラインHTMLとCLI
  tests/                       新データによる回帰・日付順評価・HTMLのテスト
  results/                     評価JSON・HTML・検証ログ（Git管理対象外）
  work/                        単一顧客の試作データなど（Git管理対象外）
```

**顧客JSON＋共有する天気・料金 → その日時までに分かった入力 → 世帯の在宅判定＋運転提案 → 前回との比較 → HTML**という流れです。エアコンにはGPSを持たせず、登録済みの設置地点IDを参照します。住居の`installation.id`と、天気共有用の`weather_site_id`は別の役割です。

## 実行方法

Python 3.12以上とOSのIANAタイムゾーン情報が必要です。実行部分は標準ライブラリのみで、Web・API・DB・Docker・ネットワークは不要です。リポジトリ直下で実行します。入力・生成物・評価結果はすべて`automation/`内に指定してください。

```bash
# 最初に1顧客で生成 → 90日再生 → HTMLを確認
python3 -B -m automation.src.cli generate --customers 1 --days 90 --seed 42 \
  --output automation/work/single/data
python3 -B -m automation.src.cli replay --data automation/work/single/data \
  --customer H001 --output automation/results/single

# 標準の100世帯×90日を再生成（編集した入力は上書きされる）
python3 -B -m automation.src.cli generate --customers 100 --days 90 --seed 42 \
  --output automation/data

# 任意の顧客だけを再評価
python3 -B -m automation.src.cli replay --data automation/data --customer H001 \
  --output automation/results/customer-check

# 100世帯の90日分を一括評価
python3 -B -m automation.src.cli replay --data automation/data \
  --output automation/results/full

# 最終時点で一度だけ評価する従来相当のモード
python3 -B -m automation.src.cli snapshot --data automation/data \
  --output automation/results/snapshot

# テスト
python3 -B -m unittest discover -s automation/tests -v
```

生成後は`automation/results/full/index.html`をブラウザへドラッグするか、ファイルとして直接開きます。HTTPサーバーは不要です。全体一覧→顧客詳細へ進み、90日の一覧、日付選択、前/次の日、イベントのフィルターで移動できます。顧客画面の「入力JSONを開く」「評価JSONを開く」も相対リンクで利用できます。外部JS・CSS・フォントの取得や`fetch`を使いません。

終了コードは成功`0`、入力・実行エラー`2`です。既存の`--case`・`--all`・`--customers`と圧縮入力は廃止し、`generate`・`replay`・`snapshot`へ統一しました。旧14ケース、一括27顧客JSON、圧縮代表データ・旧大規模生成物は削除済みです。

## いつの情報を使うか

標準入力は**2026-08-02〜10-30の90日**です。各対象日を**翌日12:00（Asia/Tokyo）**に評価します。判定日は8/3〜10/31の90回です。対象日と判定日をHTMLで別々に表示します。設定は`data/dataset.json`の`evaluation_time=12:00`, `evaluation_day_offset=1`です。

[dataset.py](src/dataset.py)の`Prepared.snapshot`で、各回の入力を切り出します。

- 操作は発生日時と`received_at`の両方が判定日時までのものだけを使います。日単位の記録は`available_at`以降に利用できます。
- スマホは、在宅を調べる時刻`t`までに**観測・受信の両方**が済んだ情報のみを使います。後から届いた帰宅を使って、18:30時点の不在を在宅に書き換えません。
- 天気は`issued_at`、候補予測は`generated_at`が判定時刻までのもののみ。過去の候補予測は今後の運転案に使いません。
- 予定は`recorded_at`と`valid_from`を確認し、判定時点で有効な版を使います。不在を照合する過去の日は**その日に有効だった予定**を使います。現行開始と異なる旧予定の日は`schedule_changed`として支持から除外します。
- 応答は`responded_at`以降に反映します。それまでは`no_response`として扱い、修正後の選択値も隠します。予定の版は遡って適用しません。

そのため、HTMLには「判定時点の現行予定」と「対象日に有効だった予定」の両方があります。日付を進めても、未来の操作・予報・判断・予定版が過去の結果を変更しないことをテストしています。

## 新規提案の数え方とユーザーの反応

[replay.py](src/replay.py)は、機器・種類・曜日・温度条件で同じ提案を対応付け、変更先と現行開始が同じなら根拠が増えても「継続」とします。

| イベント | 意味 | 新規件数 |
|---|---|---:|
| `first` 初回 | 初めて成立 | +1 |
| `continued` 継続 | 同じ提案が引き続き成立 | +0 |
| `changed` 内容変更 | 開始時刻などが変更。一度途切れた後でも前と内容が異なれば変更 | +1 |
| `ended` 終了 | 条件不成立、見送り、承認、予定変更などで有効な提案がなくなった | +0 |
| `reappeared` 再出現 | 一度終了し、新しい根拠などで同じ内容が再び成立 | +1 |

各提案エピソードには`proposal_id`を付け、継続中は同じIDにします。**予冷は実行対象日を持つ一時的な候補**なので、異なる実行日の候補は別件です。同じ実行日の候補が2日間残る場合は、後の日を継続として加算しません。対象日をHTMLにも表示します。

承認・修正承認・見送り・無反応は、提案の発生とは別の`responses`として記録します。見送りは内容と根拠署名が同じ場合に抑制し、新しい根拠が加われば再評価します。承認・修正で明示的に選んだ値を優先し、その値の根拠や予測がない場合に別の値へ勝手に置き換えません。承認済みの手動案とは別に新しい不在根拠が成立した場合は、見直し相談まで消してしまわないようにします。

入力の`feedback`と`devices[].schedule_versions`は過去の事実です。CLIが承認を保存したり予定を実行したりすることはありません。予定変更も、仮データにあらかじめ入れた有効な版を読むだけです。

## 判定の固定ルールと仮データの変化

機械学習の訓練・パラメーター更新はありません。毎回、履歴の集計と固定ルールで判定します。

- **開始時刻**: 直近4回の完了した対象曜日で、候補±15分に3日以上。Web手動オンのみを使い、自動オン・温度変更・旅行・今回だけを支持票にしません。新データでは前後各5分以内の独立した電源観測で`false → true`を確認したオンに限定します。すでにオンへの再送、電源不明、間に別の電源操作がある場合は除外します。終了時刻は維持します。`engine.start_pattern`, `presence_proposals.confirmed_starts`。
- **在宅からの見直し**: 直近4回の対象曜日のうち、予定開始に世帯全員が不在だった日が3日以上。誰か在宅なら在宅、全員の外出が確認できた場合だけ不在、それ以外は不明。旅行・今回だけ・記録欠損・旧開始時刻の日は除外します。帰宅時刻だけで変更先や節約額を出しません。手動提案と同じ変更なら根拠を統合します。`presence_proposals.review_weekday`。
- **スマホ情報**: 有効期限2時間。自宅Wi-Fi接続は在宅、切断だけでは外出としません。ジオフェンス内側の継続確認は10分以上離れた複数観測が必要です。接近だけでは帰宅にせず、通過・寄り道を分けます。位置情報が不可でも、利用が有効な自宅Wi-Fiで在宅を確認できます。`presence.PresenceIndex`。
- **暑い日の温度**: 操作±30分以内の実測相当の外気温32℃以上で、同じ低い設定温度への変更が異なる3日以上。涼しい日にも同じ変更がある場合や対応が不明な場合は限定提案を見送ります。`engine.temperature_decision`。
- **予冷**: 同じ期間の候補別kWh×単価を積算し、必要時刻の予測室温が目標±0.5℃以内で、総額が厳密に下がる場合だけ提案します。観測kWhと将来候補の予測は別です。税・基本料金等は含みません。温度・電力・料金の欠損をゼロ補完しません。`engine.energy_decision`。

生成は`generate.py`と`simulation.py`を参照してください。固定seedで同じファイル内容を再現します。顧客ID・ケース名は識別用で、判定を分岐させません。観測電力は操作の稼働時間と設定温度・天気から積算します。予定変更後の自動オンも、その日に有効な開始時刻へ合わせています。

単身・複数人、複数機器、直帰・寄り道・通過、同居人のみ在宅、利用停止・一時欠損、旅行と復帰、予冷の損得を含みます。同じ顧客でも途中で帰宅・手動時刻・在宅情報の利用可否・現行予定が変わります。

## 旧テストからの移行と検証

旧データファイルを残したままのテストではなく、新しい`data/customers/*.json`を読み込むテストへ移しました。

| 従来の確認内容 | 新しい確認先 |
|---|---|
| 3/4日・±15分、証拠1回、早い開始、終了維持 | `test_dataset.py` / H015・H019 |
| 自動オンや温度変更を開始にしない、時刻の分散 | H014・H016 |
| 初回予定の開始・終了・温度が共通する日 | H017 |
| 暑い日の温度、涼しい日の反証、温度/天気欠損 | H013・H023と入力変更テスト |
| 安い予冷、高い予冷、快適性不足、電力/料金/室温欠損 | H011・H020〜H022と入力変更テスト |
| 未利用のゼロと欠損、自動実行、旅行・例外の除外 | H009・H010・H022 |
| 同居人在宅、全員外出、不明、通過、寄り道、受信遅延 | `test_signals.py`と顧客別テスト |
| 最初の判定日と根拠、継続の非重複、見送りと再評価 | `TemporalReplayTests` / H001・H008 |
| 未来の操作・予報・判断・予定が過去を変えない | `test_dataset.py`, `test_report.py` |
| 固定seed、1顧客と100顧客で同じ入力、HTML内包と相対リンク | `test_report.py` |

予定・操作を固定して在宅情報だけを変えるテスト、別顧客への影響がないこと、同じ実行日の予冷が2日残っても重複計上しないことも確認します。HTMLはChromiumで直接開き、90日の選択、一覧からの遷移、フィルター、JavaScriptエラーなしを確認しています。レポートの使用にNodeやPlaywrightは必要ありません。

集計と計測値は、生成した`results/full/summary.json`を参照してください。`new_proposal_count`は継続・承認・見送りを除く新規エピソード数、`decision_day_reason_counts`は機器・曜日・種類・判定日ごとの判定回数です。比較対象の期間・日数が異なるため、以前の最終時点だけの件数とは直接比較しません。評価時間にHTMLの書き出し時間は含めません。
