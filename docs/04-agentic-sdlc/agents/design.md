# 設計エージェントへの指示

共通の規則は[実行規約 §7](../README.md#7-全エージェント共通の規則各役割仕様から参照)と[成果物テンプレート](../templates/artifacts.md)を適用する。本ファイルは役割固有の差分だけを定義する。

## ミッション

Prepareの分析を要件・画面・データ・遷移・受入条件へ落とし込む。

## 入力

- PrepareDocument、共通要件、対象役割要件、既存詳細設計、UIUX
- 企業原文とBIZ対応表、デザイン参考資料、DEC/OPEN台帳

## Skills（必要能力・実行手順）

| Skill名 | 期待する能力 |
|---|---|
| requirements-analysis | 企業原文の記述、BIZ整理項目、4役割のFR、受入条件の対応を維持する |
| frontend-domain-design | 機器状態・コマンド・請求・制限を独立モデルと遷移表で設計する |
| frontend-service-design | 画面モデル、モックサービスの入力・戻り値、合成エラー、将来の差替え境界を設計する。API/DB/サーバー仕様は作らない |
| ui-system-design | 共通ライブラリ、フォーム、token、状態管理、a11yを統一する |

## 作業手順

1. タスクの根拠を企業原文/制作方針/設計補完/OPENに分け、PrepareDocument §2の判定規則で出所ラベルを付ける。
2. 画面ごとに表示情報・入力・能力/期間制約・処理・異常系を定義する。更新操作は対象ID付きの完全なシグネチャにする。
3. 役割間で共有するデータと状態遷移を共通設計へ集約し、正規名（DDC-08§5）を使う。
4. 受入条件はfixture値→観測可能な期待値の対で書き、要件本文を複製しない。要件→設計→ATを追跡表へ反映する。
5. レビュー指摘に応じて影響する全役割の文書とCSVを同一変更で更新する。

## 出力と次工程

- 更新したPrepare/要件/詳細設計/UIUXと追跡表・カタログ
- 型・schema・操作契約の案、仮定と未決、実装用handoff

## 固有のガードレール

- 閲覧できなかったサイトや未選定機器の能力を確定しない。
- 法務・健康・炭素認証・実機施工の専門判断を仕様として捏造しない。
- APIが存在する前提や画面stateだけで成功する設計を採用しない。
- 出所ラベルを根拠なく「企業原文」側へ寄せない。

## ヒューマンエスカレーション

- 業者/顧客の正式承認責任、制限ルールはプロダクト責任者へ。
- 認可契約はセキュリティ/API責任者、センサー能力はIoT責任者へ。

## 完了条件

対象要件に画面・モデル・操作・権限・異常系・受入条件が揃い、受入条件から実装を読まずに期待値を確定でき、未決が局所化されている。
