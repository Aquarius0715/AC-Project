# デバイスファームウェア要件: ESP32 エアコンノード (PoC)

バージョン: 0.5.0 / 作成日: 2026-11-05 / 更新日: 2026-11-10 (ファームウェア 0.4.0 `service/device/main.cpp` に合わせた) / 状態: レビュー用ドラフト / 言語: 日本語 (英語版: [device-firmware.md](device-firmware.md))

この文書だけで完結します。ファームウェア担当者に、ESP32 ノードが行うべきことを伝えるものです。他の文書は不要です。0.5.0 から、形式は実装済みのファームウェア 0.4.0 のものです。以前の版の要望をファームウェアが満たしていない箇所は、§8 に挙げています。

## 1. 概要

Web プラットフォームがエアコン (AC) を表示・制御します。AC 1 台につき ESP32 の**ノード**が 1 台あります。ノードとプラットフォームは **MQTT ブローカー**だけを介して通信します (ブローカーのアドレスと認証情報は別途渡します)。

```
Web プラットフォーム <--- MQTT ブローカー ---> ESP32 ノード --IR--> AC (Daikin)
                                                   |
                                     BME680 / PM2.5 / PZEM センサー
```

ノードの仕事は 3 つです。

1. コマンド (電源、温度、モード、風量) を受け取り、赤外線 (IR) で AC に送る。
2. センサーの計測値を 5 秒ごとに報告する。
3. 生きていること (ハートビート) と、AC に最後に送った設定を報告する。

現在ノードは 2 台です。ファームウェアは同じバイナリで、`config.h` の `NODE_ID` だけが違います。各ノードは見つけたパーツをハートビートで報告します (§5.1)。

| ノード | `node_id` | パーツ |
|---|---|---|
| 1 | `node_1` | IR LED (`ir`)、BME680 (`bme680`)。IR LED で AC を操作する。 |
| 2 | `node_2` | BME680、PM2.5 センサー (`pm25`、I²C 0x19 の DFRobot 空気質センサー)。IR なし。PZEM 電力計 (`pzem`) は配線され電源が入っているときのみ。 |

プラットフォームは、`node_id` からそのノードがどの AC のものかを知ります。HQ が管理アプリで、各デバイスにノードが使う **MQTT ノード ID** を登録します（ファームウェアの設定どおり。英字の大文字小文字、数字、`-`、`_`が使え、1 つの ID は 1 台のデバイスだけです）。ID が登録されていないノードは受信されても記録されません。新しいノードの追加にプラットフォームのリリースは要らず、この登録だけで済みます。

対象外: TLS、ノードごとの認証情報、OTA 更新。トピック `…/sensors` と `…/command`、および最初のスケッチの文字列コマンドは引き続き使えます。

## 2. MQTT トピック

すべてのトピックは `smarthome/ac/<node_id>/` で始まります。特に記載がなければ、ペイロードは UTF-8 の JSON です。PubSubClient は QoS 0 でしか公開できないため、ノードが送るものはすべて QoS 0 です。

| トピック (接頭辞より後) | 方向 | QoS / retain | 内容 |
|---|---|---|---|
| `sensors` | ノード → プラットフォーム | 0 / なし | センサーの計測値 (§5.2)、およびオフライン中に保持した計測値 (§6) |
| `command` | プラットフォーム → ノード | 1 / なし (ノードは QoS 0 で購読) | コマンド (§3) |
| `command/result` | ノード → プラットフォーム | 0 / なし | コマンド 1 件の結果 (§3.4) |
| `state` | ノード → プラットフォーム | 0 / **retained** | AC に最後に送った設定 (§4) |
| `status` | ノード → プラットフォーム | 0 / **retained** | ハートビートと遺言 (§5.1) |

プラットフォームは、ノードから 3 分間何も届かないとき、またはブローカーがそのノードの遺言を送ったとき (§5.1) はすぐに、そのノードを**オフライン**とみなします。5 秒ごとの計測値と 60 秒ごとのハートビートで、オンラインが保たれます。

## 3. 制御: `…/command`

### 3.1 要望

| ID | 要望 |
|---|---|
| DEV-01 | **電源の ON / OFF。** |
| DEV-02 | **温度を指定した値に設定**する。16〜30 °C、1 °C 刻み (例: 「26 度」)。 |
| DEV-03 | **運転モード** (`cool`、`dry`、`fan`、`auto`) と **風量** (`auto`、`low`、`mid`、`high`) の設定。 |
| DEV-04 | 1 つの JSON コマンドでこれらのどれでも指定できる。省略した項目は現在の値を保つ。従来の文字列コマンドも使える。 |
| DEV-05 | すべてのコマンドに対し、`…/command/result` に**結果**をちょうど 1 つ返す。範囲外の値は `invalid` とし、IR は送らない。 |
| DEV-06 | IR コマンドは 1 秒に 1 件まで。最後に送ったコマンドから 1 秒以内に来たものには `invalid` を返す。 |

### 3.2 JSON コマンド

```json
{"commandId":"7f3c…","power":"ON","temp":26,"mode":"cool","fan":"auto"}
```

| 項目 | 型 | 値 | 省略時 |
|---|---|---|---|
| `commandId` | 文字列 | 任意の文字列。結果にそのまま返す | 結果は `null` |
| `power` | 文字列 | `ON` / `OFF` | 現在の値を保つ |
| `temp` | 整数 | 16〜30 | 現在の値を保つ |
| `mode` | 文字列 | `cool`、`dry`、`fan`、`auto` | 現在の値を保つ |
| `fan` | 文字列 | `auto`、`low`、`mid`、`high` | 現在の値を保つ |

- 温度だけの変更: `{"commandId":"…","temp":26}` は設定温度だけを変え、電源・モード・風量は今のままにする。
- ノードは、現在の設定に新しい項目を当てはめた **IR フレームを 1 つ**送る。電源が `OFF` の間は OFF フレームを送り、新しい設定は次の `ON` のために保つ。
- 初回起動時の設定: OFF、`cool`、24 °C、風量 `auto`。
- ペイロードが JSON オブジェクトとして読めれば JSON コマンド、それ以外は文字列コマンド (§3.3)。
- プラットフォームは、1 つのコマンドに 1 つの設定 (電源、`temp`、`mode`、`fan` のいずれか) とコマンド ID を入れて送る。値はプラットフォームのものだけ (モード `cool`、`dry`、`fan`、風量 `low`、`mid`、`high`)。ファームウェアのバージョン付きのハートビート (§5.1) をまだ送っていないノードには、文字列コマンド (電源のみ) を送る。

### 3.3 文字列コマンド (既存)

`ON`、`OFF`、`COOL24` (ON、冷房、24 °C、風量 `auto`)。前後の空白と大文字小文字は無視する。JSON コマンドと同様に結果を返し、`commandId` は `null`。

### 3.4 結果: `…/command/result`

IR フレームと新しい `state` を送った後、IR を送らない場合はすぐに送る。

```json
{"commandId":"7f3c…","command":"<受け取った文字列>","result":"sent","at":"2026-11-05T12:00:01+07:00"}
```

| `result` | 意味 |
|---|---|
| `sent` | IR フレームを送った。(IR は一方向なので、AC が従ったことの証明ではない。) |
| `unsupported` | 知らない文字列コマンド、または JSON オブジェクトでないペイロード。 |
| `invalid` | 値が範囲外または上記の語でない、またはレート制限 (DEV-06)。 |

`at` はノードの時刻 (§5.2) で、NTP の同期前は `N/A`。未知のコマンドはシリアルポートにもログを出す。プラットフォームは `sent` をコマンドの受領 (ack)、`invalid` / `unsupported` を拒否として扱う。結果が届かないコマンドは期限切れで終わる。

## 4. 状態: `…/state` (retained)

| ID | 要望 |
|---|---|
| DEV-10 | コマンドを送信するたびに、AC に最後に送った設定を公開する。 |
| DEV-11 | 設定をフラッシュ (`Preferences`、名前空間 `ac_state`) に保存し、起動時に復元する。再起動後の `ON` で最後の設定が送られるようにする。ブローカーに接続するたびに `state` をもう一度公開する。 |

```json
{"power":"ON","temp":26,"mode":"cool","fan":"auto"}
```

値は §3.2 の語です。これは「ノードが送った内容の記録」にすぎず、AC から読み戻したものではない。プラットフォームはこの設定をユニットに表示する。`auto` モードと `auto` 風量にはプラットフォームの値がないため、不明と表示する。

## 5. ハートビートとセンサー

### 5.1 ハートビート: `…/status` (retained)

| ID | 要望 |
|---|---|
| DEV-20 | 接続時と 60 秒ごとに**ハートビート**を送る。 |
| DEV-21 | 同じトピックに**遺言 (Last Will)** `{"online":false}` (retained) を登録し、ノードの切断をプラットフォームがすぐに知れるようにする。 |

```json
{"online":true,"fw":"0.4.0","ip":"192.0.2.50","rssi":-52,"uptime_s":123,"parts":{"ir":true,"bme680":true,"pm25":false,"pzem":false}}
```

`parts.ir` は `node_2` 以外のノードで true。`bme680` と `pm25` は起動時にセンサーが応答したとき true。`pzem` は電力計が電圧を読めているとき true。

### 5.2 センサー: `…/sensors`

| ID | 要望 |
|---|---|
| DEV-30 | 5 秒ごとに計測値を送る。 |
| DEV-31 | 存在しない、または故障したセンサーは**項目ごと省く** (キーを入れない)。「未計測」を `0` で送らない。`0` を送るのは、実際に `0` を計測したときだけ。 |
| DEV-32 | すべてのメッセージに NTP 由来の `timestamp` を付ける。オフセット付き ISO-8601 で `YYYY-MM-DDTHH:MM:SS+07:00` (NTP の同期前は `N/A`)。遅れて届いても正しい時刻で記録できるようにするため。 |
| DEV-33 | PZEM の項目 (`voltage`、`current`、`power`、`energy`) は、電力計が 0 より大きい電圧を読めている間だけ送る。 |

```json
{"node_id":"node_2","timestamp":"2026-11-10T17:35:26+07:00","temp":25.6,"humidity":43.8,"pressure":1008.0,"gas":423837,"approx_altitude":43.9,"pm25":55}
```

| キー | 単位 | 小数桁 | パーツ |
|---|---|---|---|
| `node_id` | — | — | ノードの `NODE_ID` |
| `temp` | °C | 1 | BME680 |
| `humidity` | % | 1 | BME680 |
| `pressure` | hPa | 1 | BME680 |
| `gas` | Ω | 0 | BME680 |
| `approx_altitude` | m | 1 | BME680 |
| `pm25` | µg/m³ | 0 | PM2.5 センサー |
| `voltage` | V | 1 | PZEM |
| `power` | W | 1 | PZEM |
| `current` | A | 3 | PZEM |
| `energy` | kWh | 3 | PZEM |

プラットフォームが記録するのは `temp`、`humidity`、`pm25`、`power` です。最初のスケッチのメッセージ (`device_id`、オフセットのない timestamp、計測しないものは `0`) も引き続き読みます。その場合、温度・湿度・電圧の `0` は未計測とみなします。

## 6. オフラインバッファ (蓄積と再送)

ブローカーに届かない間、ノードは計測値を保持し、再接続後に送信します。

| ID | 実装 (ファームウェア 0.4.0) |
|---|---|
| DEV-40 | 切断中、および `publish()` が失敗したとき、計測値は **RAM** の 50 件のバッファに入る (5 秒ごとで約 4 分)。再起動や電源断で失われる。 |
| DEV-41 | 再接続後、ハートビートと `state` のすぐ後に、保持した計測値を**古い順**に 50 ms 間隔で、最新の計測値より先に送る。`publish()` が失敗したらそこで止め、残りは保持する。 |
| DEV-42 | 再送するメッセージは元のまま (QoS 0、追加項目なし)。`timestamp` は元の計測時刻。プラットフォームは、`timestamp` が到着より 1 分を超えて古い計測値を、その `timestamp` の分に記録する。 |
| DEV-43 | バッファがいっぱいになると、**新しい**計測値を捨てる (古い 50 件が残る)。 |
| DEV-44 | NTP の同期前の計測値は `timestamp` が `N/A` で、プラットフォームは到着時刻で記録する。 |
| DEV-45 | バッファするのは計測値だけ。コマンドは遅れて再実行しない。`status` と `state` は retained なのでバッファ不要。 |

## 7. 堅牢性と設定

| ID | 要望 |
|---|---|
| DEV-50 | Wi-Fi と MQTT は、メインループを**止めずに**自動で再接続する (バックオフ付きで再試行、1 秒〜30 秒)。ブローカー停止中もセンサーの読み取りを続ける。接続のたびに `…/command` を再購読する。 |
| DEV-51 | `node_id` は 1 か所の設定とする。`node_id` 項目、トピック、MQTT クライアント ID (`ac-<node_id>`)、ログの接頭辞はすべてそこから決める。 |
| DEV-52 | Wi-Fi、ブローカーのアドレス、`node_id` をスケッチに直書きしない (`config.h` にある。PoC では現在の値を初期値として残してよい)。 |
| DEV-53 | MQTT のパケットサイズを計測値が入る大きさにする (`setBufferSize(1024)`。PubSubClient の既定は 256 で、超えると黙って失敗する)。計測値の `publish()` が失敗したら、その計測値をオフラインバッファへ回す。 |
