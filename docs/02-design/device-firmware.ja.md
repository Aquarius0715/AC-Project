# デバイスファームウェア要件: ESP32 エアコンノード (PoC)

バージョン: 0.4.0 / 作成日: 2026-11-05 / 状態: レビュー用ドラフト / 言語: 日本語 (英語版: [device-firmware.md](device-firmware.md))

この文書だけで完結します。ファームウェア担当者に、ESP32 ノードが行うべきことを伝えるものです。他の文書は不要です。

## 1. 概要

Web プラットフォームがエアコン (AC) を表示・制御します。AC 1 台につき ESP32 の**ノード**が 1 台あります。ノードとプラットフォームは **MQTT ブローカー**だけを介して通信します (ブローカーのアドレスと認証情報は別途渡します)。

```
Web プラットフォーム <--- MQTT ブローカー ---> ESP32 ノード --IR--> AC (Daikin)
                                                   |
                                          BME680 / PZEM センサー
```

ノードの仕事は 3 つです。

1. コマンド (電源、温度、モード、風量) を受け取り、赤外線 (IR) で AC に送る。
2. センサーの計測値を 5 秒ごとに報告する。
3. 生きていること (ハートビート) と、AC に最後に送った設定を報告する。

現在ノードは 2 台です。ファームウェアは同じバイナリで、設定だけが違います。

| ノード | `node_id` | パーツ |
|---|---|---|
| 1 | `node_1` | IR LED (`ir`)、BME680 (`bme680`)。電力計なし。 |
| 2 | `node_2` | BME680、PZEM 電力計 (`pzem`)。IR なし。 |

プラットフォームは、`node_id` からそのノードがどの AC のものかを知ります。HQ が管理アプリで、各デバイスにノードが使う **MQTT ノード ID** を登録します（ファームウェアの設定どおり。英字の大文字小文字、数字、`-`、`_`が使え、1 つの ID は 1 台のデバイスだけです）。ID が登録されていないノードは受信されても記録されません。新しいノードの追加にプラットフォームのリリースは要らず、この登録だけで済みます。

対象外: TLS、ノードごとの認証情報、OTA 更新。トピック `…/sensors` と `…/command`、および文字列コマンドは現行スケッチで既に動いており、これからも動く必要があります。

## 2. MQTT トピック

すべてのトピックは `smarthome/ac/<node_id>/` で始まります。特に記載がなければ、ペイロードは UTF-8 の JSON です。

| トピック (接頭辞より後) | 方向 | QoS / retain | 内容 |
|---|---|---|---|
| `sensors` | ノード → プラットフォーム | 0 / なし (再送分は QoS 1、§6) | センサーの計測値 (§5.2) |
| `command` | プラットフォーム → ノード | 1 / なし | コマンド (§3) |
| `command/result` | ノード → プラットフォーム | 1 / なし | コマンド 1 件の結果 (§3.4) |
| `state` | ノード → プラットフォーム | 1 / **retained** | AC に最後に送った設定 (§4) |
| `status` | ノード → プラットフォーム | 1 / **retained** | ハートビートと遺言 (§5.1) |

プラットフォームは、ノードから 3 分間何も届かないとそのノードを**オフライン**とみなします。そのため、少なくとも 60 秒ごとに何かが届く必要があります。

## 3. 制御: `…/command`

### 3.1 要望

| ID | 要望 |
|---|---|
| DEV-01 | **電源の ON / OFF。** |
| DEV-02 | **温度を指定した値に設定**する。16〜30 °C、1 °C 刻み (例: 「26 度」)。 |
| DEV-03 | **運転モード** (`cool`、`dry`、`fan`、`auto`) と **風量** (`auto`、`low`、`mid`、`high`) の設定。 |
| DEV-04 | 1 つの JSON コマンドでこれらのどれでも指定できる。省略した項目は現在の値を保つ。従来の文字列コマンドも使える。 |
| DEV-05 | すべてのコマンドに対し、`…/command/result` に**結果**をちょうど 1 つ返す。範囲外の値は `invalid` とし、IR は送らない。 |
| DEV-06 | IR コマンドは 1 秒に 1 件まで。超えた分は `invalid` を返す。 |

### 3.2 JSON コマンド

```json
{"commandId":"7f3c…","power":true,"celsius":26,"mode":"cool","fanLevel":"auto"}
```

| 項目 | 型 | 値 | 省略時 |
|---|---|---|---|
| `commandId` | 文字列 | 任意の文字列。結果にそのまま返す | 結果は `null` |
| `power` | 真偽値 | `true` / `false` | 現在の値を保つ |
| `celsius` | 整数 | 16〜30 | 現在の値を保つ |
| `mode` | 文字列 | `cool`、`dry`、`fan`、`auto` | 現在の値を保つ |
| `fanLevel` | 文字列 | `auto`、`low`、`mid`、`high` | 現在の値を保つ |

- 温度だけの変更: `{"commandId":"…","celsius":26}` は設定温度だけを変え、電源・モード・風量は今のままにする。
- ノードは、現在の設定に新しい項目を当てはめた **IR フレームを 1 つ**送る。
- `power:false` は OFF フレームを送り、他の設定は次の `power:true` のために保つ。
- 初回起動時の設定: ON、`cool`、24 °C、風量 `auto`。
- ペイロードが `{` で始まれば JSON。

### 3.3 文字列コマンド (既存)

`ON`、`OFF`、`COOL24` (冷房、24 °C)。前後の空白と大文字小文字は無視する。JSON コマンドと同様に結果を返し、`commandId` は `null`。

### 3.4 結果: `…/command/result`

IR フレームを送った後、IR を送らない場合はすぐに送る。

```json
{"commandId":"7f3c…","command":"<受け取った文字列>","result":"sent","at":"2026-11-05T12:00:01+07:00"}
```

| `result` | 意味 |
|---|---|
| `sent` | IR フレームを送った。(IR は一方向なので、AC が従ったことの証明ではない。) |
| `unsupported` | 未知のコマンド、またはこのノードに IR がない (`node_2`)。 |
| `invalid` | JSON が壊れている、値が範囲外、またはレート制限 (DEV-06)。 |

未知のコマンドはシリアルポートにもログを出す。

## 4. 状態: `…/state` (retained)

| ID | 要望 |
|---|---|
| DEV-10 | コマンドを送信するたびに、AC に最後に送った設定を公開する。 |
| DEV-11 | 設定をフラッシュに保存し、起動時に復元する。再起動後の `ON` で最後の設定が送られるようにする。保存された設定があれば、起動時に `state` をもう一度公開する。 |

```json
{"power":true,"celsius":26,"mode":"cool","fanLevel":"auto"}
```

これは「ノードが送った内容の記録」にすぎず、AC から読み戻したものではない。

## 5. ハートビートとセンサー

### 5.1 ハートビート: `…/status` (retained)

| ID | 要望 |
|---|---|
| DEV-20 | 接続時と 60 秒ごとに**ハートビート**を送る。 |
| DEV-21 | 同じトピックに**遺言 (Last Will)** `{"online":false}` を登録し、ノードの切断をプラットフォームがすぐに知れるようにする。 |

```json
{"online":true,"fw":"0.4.0","ip":"10.100.1.50","rssi":-52,"uptime_s":123,"parts":{"ir":true,"bme680":true,"pzem":false}}
```

### 5.2 センサー: `…/sensors`

| ID | 要望 |
|---|---|
| DEV-30 | 5 秒ごとに計測値を送る。 |
| DEV-31 | 存在しない、または故障したセンサーは**項目ごと省く** (キーを入れない)。「未計測」を `0` で送らない。`0` を送るのは、実際に `0` を計測したときだけ。 |
| DEV-32 | すべてのメッセージに NTP 由来の `timestamp` を付ける。オフセット付き ISO-8601 (例: `+07:00`)。遅れて届いても正しい時刻で記録できるようにするため。 |
| DEV-33 | `node_1` は `voltage`、`current`、`power`、`energy` を送らない (PZEM がないため)。 |

```json
{"device_id":"node_1","timestamp":"2026-11-05T12:00:00+07:00","temp":25.1,"humidity":60.0,"pressure":1010.2,"gas":123456.0,"approx_altitude":10.5}
```

| キー | 単位 | 小数桁 | パーツ |
|---|---|---|---|
| `temp` | °C | 1 | BME680 |
| `humidity` | % | 1 | BME680 |
| `pressure` | hPa | 1 | BME680 |
| `gas` | Ω | 1 | BME680 |
| `approx_altitude` | m | 1 | BME680 |
| `voltage` | V | 1 | PZEM |
| `power` | W | 1 | PZEM |
| `current` | A | 3 | PZEM |
| `energy` | kWh | 3 | PZEM |

## 6. オフラインバッファ (蓄積と再送)

ブローカーに届かない間、ノードは計測値を保持し、再接続後に送信します。

| ID | 要望 |
|---|---|
| DEV-40 | 切断中は計測値を RAM ではなく**フラッシュ**に保存し、再起動や電源断でも失われないようにする。切断中は 1 分に 1 件で十分。 |
| DEV-41 | 再接続後、保存した計測値を**古い順**に、レート制限付き (例: 毎秒 10 件) で、最新の計測値と並行して送る。最新の計測値とコマンドを待たせない。 |
| DEV-42 | 保存した計測値は QoS 1 で送り、ブローカーの受信確認が来てから 1 件ずつ削除する。再送したメッセージには `"buffered":true` を付ける。`timestamp` は元の計測時刻のままにする。 |
| DEV-43 | 保存領域がいっぱいになったら**最も古い**計測値から捨てる。容量は 48 時間分以上。 |
| DEV-44 | NTP の同期前 (有効な時刻がない間) は何も保存しない。 |
| DEV-45 | バッファするのは計測値だけ。コマンドは遅れて再実行しない。`status` と `state` は retained なのでバッファ不要。 |

## 7. 堅牢性と設定

| ID | 要望 |
|---|---|
| DEV-50 | Wi-Fi と MQTT は、メインループを**止めずに**自動で再接続する (バックオフ付きで再試行、1 秒〜30 秒)。ブローカー停止中もセンサーの読み取りを続ける。接続のたびに `…/command` を再購読する。 |
| DEV-51 | `node_id` は 1 か所の設定とする。`device_id` 項目、トピック、MQTT クライアント ID (例: `ac-<node_id>`。現状は 2 台が同じ ID で互いを切断してしまう)、ログの接頭辞はすべてそこから決める。 |
| DEV-52 | Wi-Fi、ブローカーのアドレス、`node_id` をスケッチに直書きしない (フラッシュ、または Git 管理外のヘッダーから読む。PoC では現在の値を初期値として残してよい)。 |
| DEV-53 | MQTT のパケットサイズを計測値が入る大きさにする (512 バイト以上。PubSubClient の既定は 256 で、超えると黙って失敗する)。`publish()` の結果を毎回確認し、失敗はログに残し、その計測値はオフラインバッファへ回す。 |
